# 2026-10-13：RGB-D 视觉里程计切换、TF 断连与 RTAB-Map 特征匹配失败

## 今日目标

第九章视觉 SLAM：由昨日 `/diff_drive_controller/odom` 驱动的 RTAB-Map 建图切换到 RGB-D Visual Odometry（VO），以独立实验验证视觉运动估计、TF、同步帧率和三维地图效果。运行环境：Ubuntu ARM64 虚拟机、ROS 2 Jazzy、Gazebo Harmonic、`second_robot`、`~/my_ros/chapt6_ws`、RTAB-Map + RViz 软件渲染。

## 今日实际完成/观察

1. 讨论并确定定位/导航/稠密重建模块边界：RTAB-Map 的视觉里程计用于估计短期运动，SLAM 后端提供回环和优化；RViz 中的 MapCloud/MapGraph 是 RTAB-Map 地图的显示插件，不是另一个 SLAM 算法；三维点云/TSDF 不自动等同 Nav2 可用的二维障碍地图。本日未开展导航或 TSDF 实施。
2. 从轮式里程计建图脚本分出 `scripts/rgbd_visual_mapping.sh`（Ubuntu 实验脚本，仓库尚未同步源文件），目标参数 `visual_odometry:=true`、`icp_odometry:=false`、`odom_topic:=/rgbd_odom`、`vo_frame_id:=odom`、`frame_id:=base_footprint`、`publish_tf_odom:=true`、`publish_tf_map:=true`、`rtabmap_viz:=false`、`rviz:=true`、`use_sim_time:=true`；软件渲染 `LIBGL_ALWAYS_SOFTWARE=1` 与 `GALLIUM_DRIVER=llvmpipe`。差速控制器实验配置建议 `enable_odom_tf: false`，避免重复 `odom→base_footprint` TF。**最终实际 YAML/脚本全文未回传，本记录不声称逐项核实生效。**
3. 排除了几个启动阻碍：`Permission denied` 通过赋予脚本执行权限处理；`.rgbd_mapping.lock` 冲突用 `fuser -v` 查到旧 `ros2`、`rgbd_sync`、`rtabmap`、`point_cloud_xyzrgb` 进程，正确退出旧建图任务，不应直接删锁文件；一次 ROS Launch 异常报告 `invalid condition expression ... got 'tru'`（缺少 e 的布尔参数），后续 RViz 成功启动，但没有保存最终具体修正行。
4. 成功接收到 `/rgbd_odom`，消息头 `frame_id=odom`，`child_frame_id=base_link`（**修改跟踪 frame 前**采样）；初始位姿接近 0。单帧正确不等于视觉跟踪稳定。
5. 初始 `view_frames` 显示两棵树：`map→odom` 与 `base_footprint→base_link→camera_link→camera_optical_frame`。将 VO/SLAM 跟踪的 `frame_id` 改为 `base_footprint` 后，截图曾确认完整链路：`map→odom→base_footprint→base_link→camera_link→camera_optical_frame`。之后再次生成的 TF 树又缺少 `odom→base_footprint`，而静态机体/相机 TF 仍在；说明动态 odom TF **间歇性**缺失，而非 URDF 每次自动改写。
6. 观察到性能变化：早期 `/rgbd_odom` 约 0.12～0.28 Hz，最长等待约 27.555 秒；随后测试达到约 3.16～3.59 Hz，`/camera/image` 约 8.672 Hz；后续 `/rgbd_odom` 观测到约 2.57～3.47 Hz、4.55～6.66 Hz 的短窗口结果。**这些数值取自不同时间、统计窗口和仿真运行状态，不能当作严格 A/B 基准**。本日所贴相机 Xacro 配置为 `<update_rate>15</update_rate>`、`640×480`；讨论过降低到 `320×240` 测性能，但最终运行文件/真实分辨率尚未核对，不能断言性能变化仅由降分辨率造成。
7. 最关键的日志：`rgbd_odometry` 多次出现 `Registration failed: Not enough inliers 0/20 (matches=2)`，另有 `matches=10`、`matches=12`；`Odom: quality=0`；RTAB-Map 报 `RGB-D SLAM mode is enabled, memory is incremental but no odometry is provided. Image 0 is ignored!`。匹配计算先以 guess 尝试、失败后再次无 guess 仍失败。日志中的 `guess=xyz≈94,-0.14,11, rpy≈0.15,-0.01,-2.68` 值可疑，但 **guess 不等于 Gazebo 真实位姿**，须检查它来自内部运动预测还是外部里程计/TF。
8. 在 TF 断开的期间，`/rgbd_odom` 仍有约 3～5 Hz 的消息，而一次 `pose.covariance` 采样显示 6×6 对角线均为 `9999`。结合匹配失败日志，强烈支持 **节点仍发布无效视觉里程计消息，而动态 TF 不再有效更新** 的解释；不能只用 `ros2 topic hz` 判断视觉里程计“工作正常”。已发现 `/rtabmap/odom_info`、`/rtabmap/odom_info_lite` 话题，**但还没有拿到 lost/features/matches/inliers 的完整消息输出**。

## 学到的接口与机制

- `/camera/image` + `/camera/depth_image` + `/camera/camera_info` 经 RGB-D 同步用于视觉前端；`/camera/points` 是独立的点云通道，**不是当前 RTAB-Map 视觉里程计的直接输入**。
- `/rgbd_odom` 的 `nav_msgs/Odometry` header 有 `frame_id/child_frame_id`，**不等于相应 TF 必然存在**。必须结合 `view_frames`、`tf2_echo` 与 TF 发布者检查。
- `map→odom` 应由 SLAM/定位系统单一发布，`odom→base_footprint` 应由本次视觉里程计单一发布，`base_footprint→base_link` 及相机静态链由 robot_state_publisher 提供；禁止临时发布静态 `odom→base_footprint` 掩盖故障。
- `ros2 topic hz` 是接收频率（墙钟时间），不能证明消息内容有效；相机 `update_rate` 是仿真时间的目标值。性能比较要同时记录 Real Time Factor、Topic hz、QoS/时间戳和有效里程计比例。
- 数据检查层级：原始 RGB/Depth/CameraInfo → 同步 → visual front-end 的 features/matches/inliers → 有效 /rgbd_odom → 动态 TF → RTAB-Map 图优化和 MapCloud。
