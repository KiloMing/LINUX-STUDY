# 2026-10-12：RGB-D / RTAB-Map 三维建图排错与 Gazebo 场景实验

## 今日目标

沿第九章 RGB-D 应用路线，在已跑通激光雷达 SLAM / Nav2 的差速机器人上测试 RTAB-Map 三维建图；针对原地旋转相对稳定、直线移动后重影/漂移的问题，比较不同场景，明确下一轮要验证的传感器、TF、里程计和同步环节。

## 今日结果（已观察到的事实）

- 在 Ubuntu ARM64 虚拟机的 ROS 2 Jazzy + Gazebo Sim 环境中，RTAB-Map GUI 能显示 RGB 图像及 3D Map；新旧场景中都有大量白色条纹、墙体/家具重影和空间结构错位。
- 在原始较简单的场景中，学习者观察到“原地旋转基本正常，机器人平移后地图开始漂移”。更换复杂场景后仍未消失。**复杂度不足不能作为唯一根因。**
- 测试了基于 SDF 原生几何体的 `ca_living_world.sdf`：包含分区、家具、彩色视觉标记；本次会话生成了候选世界文件，并在截图中看到 Gazebo 已加载类似布局。所附启动代码的世界文件路径为 `mybot_description/worlds/ca_living_world.sdf`；世界名与 `ros_gz_sim create -world` 必须一致。候选文件尚未从 Ubuntu 实际工作区同步到本仓库。
- RTAB-Map GUI 多次提示 `Loop hypothesis ... rejected!`（截图包括候选节点 9、35、32）。这只表示回环候选未通过验证，**不等于已定位地图畸变的根因**。
- Gazebo GUI 截图中实时运行率约 33%～41%，虚拟机负载偏高。需要实测图像实际频率、队列和时间戳，不能单凭此数值判定时间同步错误。

## RTAB-Map 实际启动链路

学习者提供的 `rgbd_mapping.sh` 采用文件锁避免重复启动，每次运行在 `maps/rgbd_时间戳_随机后缀/` 下创建单独 `rtabmap.db`，避免直接复用旧数据库。核心配置：

```bash
ros2 launch rtabmap_launch rtabmap.launch.py \
  use_sim_time:=true frame_id:=base_link \
  odom_topic:=/diff_drive_controller/odom \
  rgb_topic:=/camera/image depth_topic:=/camera/depth_image \
  camera_info_topic:=/camera/camera_info \
  visual_odometry:=false icp_odometry:=false \
  subscribe_scan:=false subscribe_scan_cloud:=false \
  rgbd_sync:=true approx_rgbd_sync:=false approx_sync:=true \
  qos:=2 localization:=false publish_tf_map:=true \
  database_path:="$run_dir/rtabmap.db" rtabmap_viz:=true rviz:=false
```

**关键结论：当前连续运动估计来自差速控制器轮式 odom，而不是 RGB-D visual_odometry 或 ICP odometry。** RGB-D 图像用于 RTAB-Map 建图/匹配/回环，不能把当前漂移直接归因于“视觉里程计算法”。
历史激光 SLAM 用过同一 odom，10 月 4 日曾有一次直线 Gazebo 位移约 5.65768 m / odom 约 5.660 m 的对照结果，降低了严重轮径比例错误的可能性；但是激光扫描匹配能够校正误差，且今天没有独立测量当前运动轨迹，因此**不能据此证明所有时刻 odom 完全准确**。

## RGB-D 消息与相机 Xacro 核对

已读取 ROS2 话题头（分别、顺序执行 `--once`）：

| 话题 | frame_id | 样本时间戳（仿真秒） |
|---|---|---:|
| `/camera/points` | `camera_optical_frame` | 474.864 |
| `/camera/depth_image` | `camera_optical_frame` | 478.424 |
| `/camera/camera_info` | `camera_optical_frame` | 481.712 |

这些样本来自**顺序执行的不同时间点**，不能用相差几秒认定消息不同步。还需要检查 RGB 图像 header 和同一时间窗口下的 RGB/Depth/CameraInfo 关联。

学习者当天贴出的 `camera_xacro` 关键配置：

- `camera_joint: base_link → camera_link`，平移/旋转由宏的 `xyz/rpy` 调用参数指定，调用处仍待核验。
- `camera_optical_joint: camera_link → camera_optical_frame`，固定旋转 `rpy="-1.57079632679 0 -1.57079632679"`，**是常见 ROS optical frame 旋转约定**，不应凭截图再随意增加 90°。
- 冗余辅助坐标系 `second_robot/base_footprint/camera_sensor` 以恒等变换接在 `camera_link`；建议确认没有依赖后清理，不能认定它本身造成畸变。
- Gazebo `rgbd_camera`：`<gz_frame_id>camera_link</gz_frame_id>`、`<optical_frame_id>camera_optical_frame</optical_frame_id>`、`horizontal_fov=1.047`、`640×480`、`clip=0.1～10.0 m`、`update_rate=120 Hz`。
- **建议中的修改（尚未在实际工程中验收）：** 保留 optical 旋转，暂把更新率降为 15 Hz；必要时后续单独测试 320×240。不能把“建议修改”写成“已经修好”。

注意：截至本次 GitHub 检查，仓库归档的 `ros2/chapt6_ws/src/mybot_description/urdf/second_robot/sensor/camera.urdf.xacro` 仍为旧配置（30 Hz，未含今天展示的完整 optical/兼容 frame）；Ubuntu 工作区中的最新源码和最终 launch 尚未同步。本次只提交学习记录，不以旧源码替换用户虚拟机中已运行的版本。

## 下一次按顺序测试（避免同时改多处）

1. **固定机器人、先不启动 RTAB-Map。** RViz `Fixed Frame=camera_optical_frame`，仅订阅 `/camera/points`，`Decay Time=0`。检查单帧墙壁/地面几何和光学 Z 轴方向；保存截图。点云局部不正常则先查传感器，不查优化器。
2. **对照激光。** RViz `Fixed Frame=base_link`，同时显示 `/scan` 与 `/camera/points`，检查视野重叠部分同一障碍物位置。把 `ros2 run tf2_ros tf2_echo base_link camera_link` 与 `... base_link camera_optical_frame` 的平移/四元数记录下来；核对 `camera_xacro xyz/rpy` 的宏调用处。
3. **检查 RGB-D 几何和同步。** 保存 `/camera/image`、`/camera/depth_image`、`/camera/camera_info` 的 header、分辨率/编码、`CameraInfo.k/p`、ROS 参数 `use_sim_time` 与各话题频率；确认同一帧的时间戳。RTAB-Map 使用 RGB+Depth+CameraInfo 重建，并非直接订阅 `/camera/points`。
4. **再测试运动。** `Fixed Frame=odom`，`/camera/points` 点云 `Decay Time=5`；慢速直行/后退，并对照 Gazebo 实际位置与 `/diff_drive_controller/odom`。如果原始点云能叠合但 RTAB-Map 图异常，再追踪 RTAB-Map 的时间配对、`map→odom` TF 发布者及图优化。
5. **单变量性能实验。** 记录 120 Hz 基线，再将深度相机 `update_rate` 改为 15 Hz 后完整停止/重启 Gazebo；比较 GUI 实时率、`ros2 topic hz`、RTAB-Map FPS 与地图质量。不要把消息墙钟频率与仿真秒频率直接混为一谈。
6. 保留带独立数据库路径的启动脚本；保存小段 rosbag、TF 树、相机 Xacro/launch 版本、完整 RTAB-Map 日志与正反向移动视频或截图，完成可复现证据。
