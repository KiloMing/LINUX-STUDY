## 1. Service 闭卷复测

今天先对前一日 C++ Patrol Service 做了短闭卷复测。

已经能说清：
- Service 的 SUCCESS / accepted 只表示“目标被服务端接受”，不表示海龟已经到达目标。
- Service callback 中收到的 Request 是一次请求数据；后续 Pose callback 仍要使用目标，因此目标坐标应保存为 Node 成员状态。

复测中暴露：
- 最初把 `target_x_/target_y_` 成员存在的理由说偏，后来纠正为 **跨 callback 持久保存状态**。
- 最初没有区分 Python `call_async + spin_until_future_complete` 与 C++ `async_send_request + response callback` 的执行模型。
- 最初误以为 `wait_for_service(1s)` 一秒后会退出；纠正为一次等待最多 1s，放在 while 中会重复检查，并会阻塞当前 callback。

这些内容只记为“复习后纠正”，仍需之后延迟复测。

## 2. Parameter：Node 的运行时配置

今天明确区分了普通 C++ 成员变量和 ROS Parameter：

```text
double k_dis_                  // C++ 成员状态
declare_parameter("k_dis")    // ROS Parameter
get_parameter("k_dis")        // 从参数系统读取
```

关键结论：
- `declare_parameter<double>("k_dis", 1.0)` 只是声明并注册 ROS Parameter，不会自动让 `k_dis_` 实时同步。
- `get_parameter("k_dis").as_double()` 是一次读取。
- 运行时 `ros2 param set` 修改的是 ROS Parameter；要同步到成员变量，需要重新读取或注册 Parameter callback。
- `add_on_set_parameters_callback` 一次可能收到多个参数，因此参数数组通常先整体校验，再统一更新成员，避免“前几个已经改了，后一个失败”的部分更新问题。

已完成：
- 独立 Parameter Node：`ros2 param list/get/set` 验证成功。
- 将 `k_dis`、`k_ang`、`max_speed` 接入 TurtleController。
- 动态设置 `k_dis=6.0` 后，控制器 callback 收到变化并更新成员。
- 使用 `rclcpp::AsyncParametersClient` 修改另一个 Node 的参数。
- 正常请求能收到 `result.successful=true`；故意发送负数参数时，服务端拒绝并返回失败原因。

今天还遇到一次 `ParameterNotDeclaredException`：声明名和读取名出现 `max_speed` / `max_speed_` 不一致。由此再次确认 **Parameter 的外部名字与 C++ 成员变量名是两套命名体系**。

## 3. Launch：从单节点到系统编排

今天完成 Launch 的核心模型：

```text
LaunchDescription
  ├─ Node(...)
  ├─ parameters=[...]
  ├─ namespace=...
  ├─ remappings=[...]
  └─ LaunchArgument / LaunchConfiguration
```

CMake 需要把 launch 目录安装到包的 share 目录，例如：

```cmake
install(
  DIRECTORY launch
  DESTINATION share/${PROJECT_NAME}
)
```

关键排错：
- C++ 中 `k_dis` 声明为 double，但 Launch 中写 `"k_dis": 3` 时被解释为 integer，触发 `InvalidParameterTypeException`；改为 `3.0` 后类型匹配。
- 两个 `turtlesim_node` 同时启动、又都使用绝对 Topic `/turtle1/pose`、`/turtle1/cmd_vel` 时发生 ROS Graph 冲突；`ros2 topic list` 只显示唯一 Topic 名，不能说明只有一个 Publisher/Subscriber。
- 使用 `ros2 topic info <topic> -v` 才能查看实际 endpoint 数量和所属 Node。
- 将 Topic 改为相对名称并给两套系统分别使用 `robot1` / `robot2` namespace 后，成功得到：
  - `/robot1/turtle1/pose`
  - `/robot1/turtle1/cmd_vel`
  - `/robot2/turtle1/pose`
  - `/robot2/turtle1/cmd_vel`

截图与运行结果显示两套 turtlesim 可以独立工作。由此确认：**namespace 能否真正隔离系统，取决于 Node 名和 Topic/Service 是否使用可解析的相对名称；硬编码绝对名称会绕过 namespace。**

今天发现 main 固定骨架和智能指针创建语法已经遗忘过一次，因此专门复习：
- `unique_ptr`：独占所有权

- `std::make_shared<T>()`：常用 shared_ptr 创建方式
- ROS2 的 `XXX::SharedPtr` 通常是对应 `std::shared_ptr<XXX>` 的类型别名

### 4.3 Service 状态设计

Service 增加目标合法性检查、Response 成功/失败语义以及：
- `target_x_`
- `target_y_`
- `has_target_`

关键状态规则：
- 合法请求：保存新目标、`has_target_=true`、返回 accepted。
- 非法请求：返回 rejected 和原因，但**不覆盖之前的有效目标**。
- 目标必须放成员变量，因为 Request callback 结束后仍要给后续 Pose callback 使用。

今日代码曾出现：

- 合法分支保存了 x/y，却漏掉 `has_target_=true`。
- `target` 一度拼成 `targer`。
- 项目需求原建议给 turtlesim 留边界；当前示例曾使用 `0 <= x,y <= 12`，后续控制器最终版需要统一范围。

## 5. CMake / package.xml：两个不同层次

今天通过真实报错重新建立构建模型：

```text
CMakeLists.txt
  → find_package：找到依赖
  → ament_target_dependencies：把依赖挂到具体 executable

package.xml
  → 描述 package 级依赖
  → colcon 据此决定 workspace 内包的构建顺序
```

实际错误：
- `REQUIRED` 拼成 `REQUOIRED`
- `ament_target_dependencies` 拼错
- `install{...}` 误写成花括号，应为 `install(...)`
- 已 `find_package(turtlesim REQUIRED)`，但一度漏把 `turtlesim` 加到 `ament_target_dependencies(controller ...)`
- 头文件误写为 `turtlesim/msg.pose.hpp`，应为 `turtlesim/msg/pose.hpp`
- `find_package(turtle_patrol_interface REQUIRED)` 一度失败：虽然接口包单独 build 成功，但 `colcon build` 时 `turtle_patrol` 和 `turtle_patrol_interface` 同时开始。根因是功能包 `package.xml` 未声明对接口包的 workspace 依赖，colcon 不知道应先构建接口包。
- 补上 `<depend>turtle_patrol_interface</depend>` 后构建顺序问题解决，功能包最终能运行。

当前截图中的 `package.xml` 已看到 interface 依赖；后续整理最终项目时仍应确认 manifest 同时完整声明 `rclcpp`、`turtlesim` 等直接依赖，而不能只以“本机能 build”作为元数据完整的证明。

## 6. 运行/调试判断方式

今天出现过：
- Fast DDS `RTPS_TRANSPORT_SHM Error / open_and_lock_file failed`
- Node 启动后终端没有任何输出

结论：
- 没有日志不等于 Node 没启动；如果代码进入 `rclcpp::spin` 且没有主动日志，本来就可能保持安静。
- 应使用 ROS Graph 验证，而不是只看终端有没有输出：
  - `ros2 node list`
  - `ros2 topic list`
  - `ros2 topic type`
  - `ros2 topic echo`
  - `ros2 topic info <topic> -v`
  - `ros2 topic hz`
  - `ros2 service list/type/call`
- SHM 警告今天未证明阻断 Service/Topic 主线，因此不把它直接当作 C++ 代码错误，也不记录为已彻底修复。
