## 今日真正掌握

### sockaddr 与 sockaddr_in

- `sockaddr_in` 是 IPv4 专用地址结构，填写 `sin_family`（地址族）、`sin_port`（端口）、`sin_addr`（IP 地址）。
- `sockaddr` 是 Socket API 的通用地址接口类型；`bind()`、`connect()` 等使用 `sockaddr*`，从而接收不同地址族的具体结构。
- 实际源码先填写 `sockaddr_in server_addr`，再传入 `reinterpret_cast<sockaddr*>(&server_addr)` 和 `sizeof(server_addr)`。转换指针不会把 IP 转换成另一种地址，也不会复制结构；内核结合地址族和长度解释内容。
- IPv6 使用 `sockaddr_in6`；不能把所有地址结构都当作 `sockaddr_in`，也不能假设 `sockaddr` 足够容纳所有地址类型。

### IPv4 地址配置

| 项目 | 今天的理解与源码对应 |
|---|---|
| `AF_INET` | 表示 IPv4；两端均用 `socket(AF_INET, SOCK_STREAM, 0)` 创建 TCP socket，并设置 `sin_family = AF_INET` |
| `htons(8080)` | 将 16 位端口从主机字节序转换为网络字节序，赋给 `sin_port` |
| `INADDR_ANY` | 服务端绑定所有本地 IPv4 接口，即 `0.0.0.0`；不是客户端要连接的具体远端地址 |
| `inet_pton` | 客户端用 `inet_pton(AF_INET, "127.0.0.1", &server_addr.sin_addr)` 将文本地址转成网络字节序的二进制地址；返回 1 才成功，0 为文本无效，-1 为错误 |

两端源码用 `memset` 清零地址结构；也可以使用 `sockaddr_in server_addr{};`。当前服务端直接赋值 `INADDR_ANY`，其值为 0；写成 `htonl(INADDR_ANY)` 能更明确表达网络字节序。服务端也可用 `inet_pton` 指定本机地址：绑定 `127.0.0.1` 只接受本机回环访问，绑定所有接口也不等于外部网络或防火墙已放行。本次没有新增外部连通性验证。

### 客户端与服务端流程

```text
客户端：socket → 配置地址 → connect → send/write → recv/read → close
服务端：socket → 配置地址 → bind → listen → accept
       → read/recv → write/send → close(client_sock)
服务结束：close(server_sock)
```

`server_sock` 是监听 fd；`accept()` 返回的 `client_sock` 是与某一个客户端通信的已连接 fd。读写数据使用已连接 fd。`listen(server_sock, 5)` 的参数涉及待接受连接队列，不代表程序已经实现五个客户端并发处理。

这些是基础通信的正确调用顺序；当前源码的 `fork()` 改动存在问题，见下文，不能把当前服务端的实际控制流程视为已验证实现。

### TCP 字节流与应用层消息边界

多次 `send/write` 不保证对应多次 `recv/read`。TCP 保持字节顺序，但不保留应用每次发送的边界；一次读取可以包含多条消息，一条消息也可以分多次读取。

今天尝试在发送文本后加 `\n`，把它约定为应用层消息结束符。**这不是 TCP 分包**，TCP 不会因为换行而保证一次发送对应一次读取。终端显示五行，也不能证明调用了五次 `recv()`。

真正按行处理消息，需要把每次收到的有效字节追加到累计缓冲区，按 `\n` 取出完整消息，并保留尚未结束的尾部等待下次读取。今天讨论了这个方法，但当前仓库源码没有累计缓冲区或按行解析逻辑；客户端当前发送的是不带换行的 `"hello server"`，不能将之前的换行实验描述为当前版本已经实现了完整消息解析。

### read/write 返回值与 buffer

`read()`、`write()` 返回类型是 `ssize_t`，返回值表达本次实际处理的字节数，不是简单的布尔成功标志。

| 返回值 | `read()`（已连接 TCP，读取长度大于 0） | `write()` |
|---|---|---|
| `> 0` | 本次实际读到的字节数 | 本次实际写入的字节数，可能少于请求长度 |
| `== 0` | 接收完已有数据后到达 EOF，对端有序关闭发送方向 | 本次没有写入字节；不能解释为对端关闭，完整发送循环要避免无进展死循环 |
| `== -1` | 失败，检查 `errno` | 失败，检查 `errno` |

socket 写入成功表示数据被本地系统接受，不等于对端应用已经读取。`write(client_sock, buffer, n)` 应发送本次读到的 `n` 字节，而不是整个数组容量；还需要检查是否短写。

每次 `read(fd, buffer, ...)` 都从传入的地址开始覆盖，这里就是 `buffer[0]`。只有前 `n` 字节是本次有效数据，后面的旧内容不会自动清零。处理完或另存上一批数据后可以复用数组；拼接消息时要把未完成的部分保存到累计缓冲区。

对于 `char buffer[1024]`，`sizeof(buffer)-1` 限制本次最多读取 1023 字节，为手动添加 `buffer[n] = '\0'` 留出空间。`read()` 不会自动添加字符串结束符；应先判断返回值，再访问下标。这里的 `sizeof` 必须针对实际数组，在接收 `char*` 的函数内不能用指针的大小代替数组容量，所以客户端函数显式接收 `size`。

`\0` 是本地 C 字符串终止符，`\n` 是本次约定的应用层分隔符，两者作用不同。当前客户端按 `size-1` 读取后补 `\0`；服务端用 `string(buffer, n)` 按长度显示，并用 `write(..., n)` 回传，不依赖 `\0`。按长度处理二进制数据时可使用全部数组容量，无需预留字符串结束符。

### socket fd 与普通文件 fd

普通文件由 `open()` 获取 fd，socket 由 `socket()` 创建，服务端还通过 `accept()` 获取连接 fd。它们都可以使用统一的 `read/write/close` 接口。在本次已连接 TCP 的普通读写中，可使用 `read/write`；`send/recv` 另提供 socket 专用的 flags 参数。

接口统一不表示对象行为完全相同：TCP 是连续字节流，不能像普通文件那样通过 `lseek()` 来回定位。普通文件读到 EOF 返回 0；TCP 接收端在对端有序关闭发送方向且已有数据读完后返回 0。

### 默认阻塞行为

本次使用普通阻塞 socket，没有设置非阻塞模式或接收超时。正常情况下：

- `accept()`：没有待接受的连接时阻塞，等待连接到来。
- `read()`：连接仍开放但暂时没有数据时阻塞，当前线程睡眠等待，不是用户代码忙循环。
- `read() == 0`：不是“暂时没有数据”，而是对端有序关闭发送方向、已有数据已读完；对端 `close()` 或 `shutdown(..., SHUT_WR)` 都可能产生这一结果。

阻塞调用仍可能因错误或信号中断返回，不能认为只会因数据到达而返回。连接复位等错误也不等于正常 EOF。上述语义以有效 fd 为前提，不能用来解释当前源码中关闭监听 fd 后的 `accept()`。

## 暴露的问题

1. 当前服务端在 `accept()` 前循环 `fork()`：子进程先 `close(server_sock)`，再对已关闭的监听 fd 调用 `accept()`；父进程直接 `continue`，不断创建子进程。该控制流程存在失败与资源耗尽风险，多客户端实现尚未完成，不能直接运行它作为回声成功的复验证据。
2. 两端 `write()` 只检查负返回值，未处理小于请求长度的 partial write。客户端 `send_message()` 返回的 0 是包装函数的状态值，并不是系统调用写入的字节数，也不能据此断言全部发送完成。
3. 客户端每轮仅调用一次 `read()`，不能保证拿到完整回声；`receive_message()` 把 0 放在普通输出分支，没有单独处理 EOF 并结束外层循环。
4. 当前版本没有按 `\n` 累计解析消息；先前终端换行现象不能作为解析器完成的证据。默认阻塞行为已学习，但没有新增专门的阻塞时序测试日志。
