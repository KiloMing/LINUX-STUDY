## 今日学习内容

### 1. GZ_IP 环境变量机制

`export GZ_IP=127.0.0.1` 把变量放入当前 shell 的环境，随后从该 shell 启动的 Gazebo 子进程继承它；已经运行的进程、其他已有终端不会自动改变。写入 `~/.bashrc` 后，需要新开相应交互 shell 或重新 source；launch 也可给子进程显式设置环境。

GZ_IP 用于 Gazebo Transport 发布话题/服务时选择本机 IP，适用于多网卡或虚拟机选错地址的情况。127.0.0.1 是本机回环地址，适合此次同一虚拟机内通信；它不代表 Mac 和 Ubuntu 共用回环地址，也不适用于直接向另一台主机发布。它不设置 ROS DDS 的 domain，也不会修复 XML、插件参数或控制器配置错误。`GZ_PARTITION` 与 `ROS_DOMAIN_ID` 是另外两层隔离设置，排查时应分别核对各进程。[Gazebo Transport 官方说明](https://gazebosim.org/api/transport/13/envvars.html)

### 2. IMU 仿真与数据理解

实际源码：`imu.urdf.xacro` 定义 `imu_link`，经 fixed `imu_joint` 安装到 base_link；主 Xacro include 后还要实例化 `imu_xacro`。仅有外观 link 不会产生测量值。当前配置为：

```xml
<gazebo reference="imu_link">
  <sensor name="imu_sensor" type="imu">
    <always_on>true</always_on>
    <update_rate>50</update_rate>
    <topic>imu</topic>
  </sensor>
</gazebo>
```

world 还需加载 `filename="gz-sim-imu-system"`、`name="gz::sim::systems::Imu"`。今天逐项修正 `<senor>` → `<sensor>`、`<updata_rate>` → `<update_rate>`、`gz::sin::system::Imu` → `gz::sim::systems::Imu`。最终观察 `/imu`。

- `orientation` 是四元数 x/y/z/w，不是四个欧拉角；接近 `(0,0,0,1)` 表示接近单位旋转。具体姿态含义还要结合参考系与传感器安装方向。
- `angular_velocity` 是各轴角速度，单位 rad/s，静止时接近零。
- `linear_acceleration` 单位 m/s²。静止、传感器 Z 向上且保留重力响应时，z≈9.8 是支撑状态下的比力读数，不是机器人正在向上加速；改变姿态会改变各轴分量。
- 三组 covariance 各描述一个 3×3 协方差矩阵。对于 ROS `sensor_msgs/msg/Imu`，全零表示协方差未知，不代表完美无噪声；第一项为 -1 表示对应估计不可用。Gazebo 原生消息与 ROS 消息需区分，并核对桥接转换。[ROS Jazzy Imu 消息定义](https://raw.githubusercontent.com/ros2/common_interfaces/jazzy/sensor_msgs/msg/Imu.msg)

已归档的 Gazebo 样本中 w≈1、角速度≈0、linear_acceleration.z=9.79999999853871。URDF 转 SDF 时 fixed joint 可能被合并，样本 frame 字符串出现 base_footprint 不等于源 Xacro 没有 imu_link。

### 3. LiDAR 与 RGBD Camera

保留已跑通 LiDAR：`gpu_lidar`、`/scan`、10 Hz、水平 360 samples、范围 0.1–10 m。其渲染依赖 world 的 Sensors 系统；不能只检查模型外观。

camera 的 `sensor type="rgbd_camera"` 配置 `<topic>/camera</topic>`，640×480、30 Hz、水平视场 1.047 rad、clip 0.1–10 m。关注四类输出：

| 话题 | 含义 |
|---|---|
| `/camera/image` | 彩色图像 |
| `/camera/depth_image` | 深度图像 |
| `/camera/points` | 点云 |
| `/camera/camera_info` | 相机标定/内参信息 |

学习时通过 Gazebo 的 Image Display 选择 `/camera/image` 验证画面，并将 world Sensors 插件的 `<render_engine>` 切到 `ogre2`。本次归档未重新操作 Image Display；不把已有话题名称等同于持续帧率或图像质量验收。若用 ROS/RViz 订阅，还需要相应 ros_gz_bridge；当前 sim_control 启动入口仅自动桥接 `/clock`。

### 4. Gazebo Twist 命令

今天发布命令出现字段缺少冒号及数字拼写错误：`0.-5` 应为 `-0.5`。Gazebo `gz topic` 使用消息文本格式，例如：

```bash
gz topic -t /cmd_vel -m gz.msgs.Twist -p 'linear: {x: 0.5}, angular: {z: -0.5}'
```

这是格式示例，实际 topic 以订阅插件配置为准；ROS `ros2 topic pub` 的消息类型/语法是另一套。旧 DiffDrive 已注释后，向上述 Gazebo 话题发消息不代表 ros2_control 会驱动车轮。

### 5. 6.5.1 / 6.5.2：ros2_control 架构与接入

| 组件 | 职责 |
|---|---|
| Controller | 根据目标与状态计算控制命令，例如差速控制器 |
| Controller Manager | 管理控制器生命周期和更新循环，协调 read/update/write |
| Command Interface | 向硬件/仿真写目标，例如轮子 velocity |
| State Interface | 读取反馈，例如轮子 position、velocity |
| Resource Manager | 加载硬件组件，管理接口及资源占用 |
| gz_ros2_control | 把 Gazebo 模型接到 ros2_control，插件实例化 Controller Manager |

创建 `urdf/second_robot/ros2_control.xacro`，主 `second_robot.urdf.xacro` 必须 include。wheel macro 使用 `${wheel_name}_joint`，调用 left/right 后实际名称为 `left_joint/right_joint`，控制配置必须逐字一致；每轮声明 velocity command 及 position/velocity state。

区分三个名字：`libgz_ros2_control-system.so` 是 Gazebo 加载的库；`gz_ros2_control::GazeboSimROS2ControlPlugin` 是 Gazebo 系统插件类；`gz_ros2_control/GazeboSimSystem` 是 ros2_control 的仿真硬件插件。正确层级如下（省略轮子接口）：

```xml
<robot xmlns:xacro="http://www.ros.org/wiki/xacro">
  <ros2_control name="GazeboSystem" type="system">
    <hardware><plugin>gz_ros2_control/GazeboSimSystem</plugin></hardware>
    <!-- left_joint / right_joint command/state interfaces -->
  </ros2_control>
  <gazebo>
    <plugin filename="libgz_ros2_control-system.so"
            name="gz_ros2_control::GazeboSimROS2ControlPlugin">
      <parameters>$(find mybot_description)/config/ros2_control.yaml</parameters>
    </plugin>
  </gazebo>
</robot>
```

`<gazebo>` 与 `<ros2_control>` 同级，`<parameters>` 必须在 Gazebo `<plugin>` 内。YAML 文件名、源码路径、安装路径、最终展开 URDF 与实际 spawn 输入需要形成同一条链。[gz_ros2_control Jazzy 官方说明](https://control.ros.org/jazzy/doc/gz_ros2_control/doc/index.html)

| Fast DDS SHM warning | DDS 共享内存传输警告；仅凭警告不足以确定具体成因 | 与 Gazebo 插件初始化错误分开检查；不把清理 SHM 当作插件修复，本次未执行全局清理 |
| `/controller_manager` 不出现 | 模型生成成功不等于控制插件初始化成功 | 先读 Gazebo error，再查 XML、YAML、版本/进程环境与模型输入 |

| `found an empty parameters file. Failed to initialize.` | 学习阶段发现源码有 ros2_control.yaml，但 share 中未安装；还出现文件名不一致 | CMake install 补 config，统一 YAML 文件名，重新 build/source，读取安装文件 |
| YAML 名称不一致 | 引用仍是 mybot_ros2_controller.yaml，实际为 ros2_control.yaml | 统一 `<parameters>` 与实际文件名 |
| 改了配置运行无变化 | 生成 `/tmp/second_robot.urdf`，却 spawn 旧 `/tmp/mybot.urdf` | 生成与 spawn 统一同一个新文件；后续 launch 从同一 robot_description 创建模型 |
| YAML 可读仍报 empty parameters | 后续实际源码发现 `<parameters>` 位于 `</plugin>` 外 | 移回 plugin 内；这是独立于 CMake 安装的另一个真实根因 |
| 管理器等待机器人描述 | 后续修复日志显示等待 `/robot_description` | 同时启动 robot_state_publisher；文件 spawn 本身不能替代描述发布，不把“只需 spawn 文件”作为通用结论 |
| 仿真时钟链路 | 后续启动入口补入 `/clock` 的 Gazebo→ROS 桥接 | 使用 use_sim_time 时同时核对 `/clock`；不据此断言所有初始化失败都由时钟造成 |
| 后台传感器渲染失败 | 修复任务记录了 X 显示授权及 ogre2 崩溃 | 继承桌面 DISPLAY/XAUTHORITY，保留 VM 渲染启动参数；不硬编码临时授权文件到仓库 |
| 诊断备份影响构建发现 | 工作区内 before 备份含重复 package | diagnostics 放 COLCON_IGNORE；归档不带 build/install/log 或整个诊断目录 |
