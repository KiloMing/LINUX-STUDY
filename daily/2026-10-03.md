## 今日学习内容

### 1. 第六章 ros2_control 收尾

完成并理解三类控制器：

- `joint_state_broadcaster`：读取各关节 state interface，发布关节状态；它不是给关节下达目标的控制器。
- `JointGroupEffortController`：通过 effort command interface 向一组关节下达力矩/作用量命令。对旋转关节，`effort` 可理解为关节轴上的力矩，而不是位置或速度。
- `diff_drive_controller`：接收底盘速度目标，将线速度和角速度转换为左右轮 velocity 目标，并根据轮子反馈计算里程计与 TF。

接口的关键区别：

| 概念 | 含义 |
|---|---|
| command interface | 控制器向硬件或仿真写入目标，如轮子的 `velocity` 或关节 `effort` |
| state interface | 控制器/广播器从硬件或仿真读取反馈，如 `position`、`velocity` |
| claimed | 接口已被某个活动控制器占用，其他控制器不能同时写同一资源 |
| unclaimed | 接口已经导出、可用，但当前没有活动控制器占用；不等于接口故障 |

`velocity` 在差速底盘中是轮速目标；`effort` 是驱动力矩目标。控制器类型必须与 URDF 中导出的 command interface 对齐。

### 2. sim_control / gz_sim_control 启动链路整合

当前 launch 已把以下环节串为同一个入口：

1. 启动 Gazebo Server/GUI 与指定 world；
2. `robot_state_publisher` 发布同一份 `robot_description`，并使用仿真时间；
3. 将 Gazebo `/clock` 桥接为 ROS2 `/clock`；
4. 将 Gazebo `/scan` 桥接为 ROS2 `sensor_msgs/msg/LaserScan`；
5. 在 Gazebo 中 spawn 机器人；
6. 自动加载并激活 `joint_state_broadcaster`；
7. 自动加载并激活 `diff_drive_controller`。

这样避免了“spawn 使用一份模型、状态发布器使用另一份模型”以及每次手工启动控制器造成的状态不一致。验证时仍要以 `ros2 control list_controllers`、实际 topic 和 TF 为准，不能只凭 launch 进程存在判定控制链路正确。

### 3. 修复仿真时间倒退

`slam_toolbox` 曾反复报告：

```text
Detected jump back in time
```

根因是 `/clock` 被重复桥接，ROS2 中同时存在多个 `/clock` publisher，收到的仿真时间序列相互覆盖并向后跳。修复原则是：**整个启动图只保留一个 Gazebo→ROS2 `/clock` bridge**。删除重复桥接后，再检查：

```bash
ros2 topic info /clock -v
```

使用仿真时间的节点（`robot_state_publisher`、控制器、RViz、`slam_toolbox` 等）应统一设置 `use_sim_time=true`。

### 4. 修复 ROS2 `/scan` 无数据

当时 Gazebo 内已有 `/scan`，ROS2 侧也能看到 bridge 进程，但 ROS2 `/scan` 没有消息。根因不是 LiDAR 配置本身，而是 `scan_bridge` 启动时遗漏：

```python
additional_env=gz_env
```

Gazebo Server 使用了显式 `GZ_IP`，但 `scan_bridge` 未继承相同环境，两个进程落在不同的 Gazebo Transport 通信环境，bridge 因而接不到 Gazebo `/scan`。给 `scan_bridge` 加入 `additional_env=gz_env` 后，Gazebo LaserScan 能正常桥接到 ROS2。

Gazebo 话题的正确列举命令是：

```bash
gz topic -l
```

排查时应分层确认：Gazebo 是否发布 → bridge 是否处于相同 `GZ_IP`/`GZ_PARTITION` 环境 → ROS2 topic 类型、QoS 与消息是否正确。

### 5. 进入第七章 7.2.1：slam_toolbox 建图

已安装并启动 `slam_toolbox`，开始理解 SLAM 所需的 topic、消息和 TF：

```text
map → odom → base_footprint → base_link → laser_link
```

- `map`：SLAM 建立的全局地图坐标系；允许通过 `map→odom` 修正累计里程计误差。
- `odom`：局部连续的里程计坐标系，适合描述短期运动，但会累计漂移。
- `base_footprint`：机器人在地面的二维投影，常作为底盘运动参考。
- `base_link`：机器人主体坐标系。
- `laser_link`：激光雷达坐标系；必须与真实安装位置、方向一致。
- `/scan`：`sensor_msgs/msg/LaserScan` 实时量测。
- `/map`：`nav_msgs/msg/OccupancyGrid` 栅格地图；常用值为未知、空闲和占用。

RViz 建图时 `Fixed Frame` 应设置为 `map`，RViz 自身也应使用仿真时间。实时 LaserScan 通过 TF 投影到 `map` 后，应与已经写入 OccupancyGrid 的墙面基本重合。
