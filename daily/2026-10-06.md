## 一、7.4.3 `NavigateToPose` 单点导航

### 1. Action 的完整语义

单点导航持续时间较长，需要中途反馈和最终状态，因此使用 Action 而不是 Topic 或普通 Service：

```text
Client 构造目标位姿
        ↓ Goal
/navigate_to_pose Action Server
        ↓ Feedback：当前位置、剩余距离等
        ↓ Result：SUCCEEDED / ABORTED / CANCELED
Client 分别处理“已接受”和“最终完成”
```

目标被 Server 接受只说明任务进入执行流程，不代表机器人已经到达。代码需要分别注册 `goal_response_callback`、`feedback_callback` 和 `result_callback`。

### 2. `frame_id` 与 yaw 单位

导航目标使用 `geometry_msgs/msg/PoseStamped`：

```cpp
goal_msg.pose.header.frame_id = "map";
goal_msg.pose.header.stamp = this->now();
goal_msg.pose.pose.position.x = target_x;
goal_msg.pose.pose.position.y = target_y;

tf2::Quaternion q;
q.setRPY(0.0, 0.0, target_yaw_rad);
goal_msg.pose.pose.orientation = tf2::toMsg(q);
```

今天解决了两个会直接破坏导航、但编译器不一定能发现的问题：

1. `frame_id` 误写成 `msp`，应为 TF 树中的 `map`；
2. `q.setRPY()` 接收弧度，不能把 90、180 这样的角度值直接当 yaw 传入。

换算关系为：

```text
yaw_rad = yaw_degree × π / 180
90° = π / 2 ≈ 1.5708 rad
```

### 3. Timer 不能重复发送 Goal

Timer 用来延迟调用 `send_goal()`，让 Executor 先运行并等待 Action Server 上线。周期 Timer 如果不取消，会每隔几秒重复发送同一目标。正确流程是：

```text
Timer 触发
    ↓
wait_for_action_server()
    ├── Server 未就绪：本轮返回，后续 Timer 再试
    └── Server 已连接：cancel Timer → 只发送一次 Goal
```

`timer_->cancel()` 应在确认 Server 可用、准备发送目标时执行。这样既容忍 Nav2 启动较慢，又避免重复 Goal、重复回调和难以解释的机器人行为。

## 二、7.4.4 `FollowWaypoints` 路点导航

### 1. 从单点扩展到 Pose 列表

`FollowWaypoints` 的 Goal 是一组按顺序执行的 `poses`。今天将点位集中存为结构体，并通过统一的 `create_pose(x, y, yaw)` 填入 `map` frame、时间戳、位置和 quaternion：

| 点位 | x | y | yaw（弧度） |
|---|---:|---:|---:|
| A | -0.507 | -0.09 | 1.62 |
| B | -3.14 | 3.11 | 1.15 |
| C | -0.497 | 6.65 | -1.94 |
| D | 1.616 | 3.33 | 2.80 |

### 2. Server 名称必须正确

```cpp
using FollowWaypoints = nav2_msgs::action::FollowWaypoints;

action_client_ = rclcpp_action::create_client<FollowWaypoints>(
    this,
    "/follow_waypoints"
);
```

如果仍连接 `/navigate_to_pose`，或凭印象写了不存在的名称，`wait_for_action_server()` 会一直失败。排查时使用：

```bash
ros2 action list
ros2 action info /follow_waypoints
ros2 interface show nav2_msgs/action/FollowWaypoints
```

### 3. Feedback 字段以本机接口为准

`FollowWaypoints` Feedback 的关键字段是当前路点索引 `current_waypoint`，不能混用 `NavigateToPose` Feedback 中的 `current_pose`，也不能照抄其他 Nav2 版本字段。

今天通过索引变化识别“上一点已到达”：

```text
第一次 Feedback：记录当前索引，不宣布任何点已完成
索引从 n 变为 n+1：说明 n 已完成，触发 n 的到点任务
Action 最终 SUCCEEDED：单独补触发最后一个点
```

最后一个点之后不会再出现“切到下一索引”的 Feedback，所以必须在成功 Result 中处理最后点，否则 D 点的语音和拍照会遗漏。

## 三、7.5 巡检控制节点

`PatrolController` 把三种 ROS 2 通信方式组合起来：

```text
FollowWaypoints Action Client
        │
        ├── Feedback/Result 判断到达 A/B/C/D
        ├── SpeechText Service Client → 到点语音播报
        └── Image Subscription → 保存当前相机帧
```

核心状态包括 `patrol_points_`、`last_waypoint_`、`current_waypoint_`、`first_feedback_`、`speech_client_`、`image_sub_`、`latest_image_` 和负责启动等待的 `timer_`。

到点行为统一收口在 `on_waypoint_reached(index)`：先校验范围并读取点名，再调用 `speak("Reached " + point.name)` 和 `save_current_image(point.name)`。这种结构避免把副作用散落在 Feedback 和 Result 两个回调中，也方便后续增加扫码、温度采集或异常上报。

Result 回调仍要完整区分 `SUCCEEDED`、`ABORTED`、`CANCELED` 和未知状态。若当前 Nav2 Result 还提供 `error_code` / `error_msg`，应在 `result.result` 非空时输出，便于定位导航业务错误。

## 四、自定义 `SpeechText` Service 与 speaker

### 1. 接口与客户端

语音请求适合用 Service：巡检控制器发出文本，speaker 执行播报并返回是否成功：

```text
# Request
string text
---
# Response
bool result
```

C++ 客户端使用 `autopatrol_interface::srv::SpeechText`，连接 `/speech_text`。调用前用短超时 `wait_for_service()` 检查服务是否存在；不存在时记录 warning 并返回，不能让整个巡检节点永久阻塞。存在时构造 Request，写入 `text`，使用 `async_send_request()`，在 Future 回调中检查 `response->result`。

### 2. rosidl 配置

自定义接口不是只创建 `.srv` 文件。接口 package 的 `package.xml` 需要生成器、runtime 和接口包分组，例如：

```xml
<buildtool_depend>ament_cmake</buildtool_depend>
<buildtool_depend>rosidl_default_generators</buildtool_depend>
<exec_depend>rosidl_default_runtime</exec_depend>
<member_of_group>rosidl_interface_packages</member_of_group>
```

CMake 侧还要 `find_package(rosidl_default_generators REQUIRED)`，并用 `rosidl_generate_interfaces()` 列出 `srv/SpeechText.srv`。缺少这些配置会导致接口不生成、头文件找不到或下游构建/运行失败。

修改接口后应先构建接口包并重新 source，再用 `ros2 interface show autopatrol_interface/srv/SpeechText` 验证，避免继续使用旧 install 空间。

### 3. speaker + `espeak-ng`

speaker 节点提供 `/speech_text` Service，把请求文本交给 `espeak-ng` 播放，再把执行结果写回 `result`。巡检控制器只依赖 Service 契约，不直接承担 TTS 细节，从而分离导航状态机和音频实现。

联调先用 `ros2 service list/type/call` 独立验证 speaker，确认能播报后再接入巡检节点。这样能区分“Service 没启动/接口不匹配”和“Nav2 没触发到点事件”。

## 五、Gazebo camera bridge

Gazebo 相机首先在 Gazebo Transport 中发布图像。要让 ROS 2 节点订阅 `/camera/image`，必须建立 bridge：

```bash
ros2 run ros_gz_bridge parameter_bridge \
  '/camera/image@sensor_msgs/msg/Image[gz.msgs.Image'
```

手动桥接只能证明参数和话题可用。最终应把 camera bridge 加入 launch，并与 `/clock`、`/scan` bridge 一样继承：

```python
gz_env = {"GZ_IP": "127.0.0.1"}
```

如果 bridge 与 Gazebo Server 的 `GZ_IP` 不一致，Gazebo 内能看到 camera topic，ROS 2 侧仍可能没有 publisher 或收不到数据。分层检查命令为：

```bash
gz topic -l
ros2 topic list | grep camera
ros2 topic info /camera/image --verbose
ros2 topic echo /camera/image --once
ros2 topic hz /camera/image
```

相机属于高频传感器。若 publisher 使用 `BEST_EFFORT` 而订阅者使用不兼容的 `RELIABLE`，双方即使都存在也可能不传消息，可用 `--verbose` 核对 QoS，必要时改用 `rclcpp::SensorDataQoS()`。但今天最终确认的直接代码错误不是 QoS，而是空指针判断写反。

## 六、`sensor_msgs/Image`、`cv_bridge` 与 OpenCV 拍照

巡检节点持续订阅 `/camera/image`，回调只把 `latest_image_` 更新为最新一帧。到点时直接保存缓存帧，延迟低、结构简单，但必须处理启动早期还没有图像的情况。

正确的空指针判断是：

```cpp
if (!latest_image_)
{
    RCLCPP_WARN(this->get_logger(), "No camera image received yet.");
    return;
}
```

修复前误写成 `if (latest_image_)`，导致**已经收到图像**时返回并打印“还没有图像”；真正没有图像时反而继续把空指针交给 `cv_bridge`。日志中的 warning 因此不是 bridge 失败的证明，反而说明指针很可能已经非空。

有图像后执行：

```cpp
auto cv_ptr = cv_bridge::toCvCopy(latest_image_, "bgr8");
bool success = cv::imwrite(filename, cv_ptr->image);
```

`cv_bridge::Exception` 表示编码/转换失败；`cv::imwrite()` 返回 `false` 表示路径、权限、编码器或写入失败，两类错误应分开报告。文件名使用 `photo_A.jpg`～`photo_D.jpg`，保存路径必须存在且可写。构建侧还需同步补齐 `sensor_msgs`、`cv_bridge` 和 OpenCV 依赖。

## 七、今日错误与排查过程

| 现象/错误 | 根因 | 修正与认识 |
|---|---|---|
| 单点导航目标不工作 | `frame_id` 误写为 `msp` | 改为 TF 树中的 `map`；字符串语义错误不一定由编译器发现 |
| 朝向异常 | 把角度直接传给 `setRPY()` | 明确接口单位为弧度，度数先乘 `π/180` |
| 同一 Goal 周期性重复发送 | wall timer 持续触发 | Server 可用后先 `timer_->cancel()`，再发送一次 Goal |
| 路点客户端一直等不到 Server | 名称写错或仍沿用单点导航名称 | 用 `ros2 action list/info` 确认 `/follow_waypoints` |
| Feedback 字段编译失败 | 混用 Action 类型字段或参考其他版本 | 用本机 `ros2 interface show`，采用 `current_waypoint` |
| 最后一点没有触发到点任务 | 只依赖索引切换 | 在 `SUCCEEDED` Result 中补处理最后一点 |
| 自定义 Service 头文件/接口生成失败 | rosidl 生成、runtime、group 或 CMake 配置不全 | 完整配置接口包，先构建接口并重新 source |
| 找不到 `/speech_text` | speaker 未启动、环境未 source 或名称不一致 | 先用 CLI 独立验证 Service，再接导航回调 |
| Gazebo 有相机，ROS 2 没话题 | 未建立 camera bridge | 手动验证后将 bridge 写进 launch |
| bridge 存在但无数据 | bridge 与 Gazebo Server 的 `GZ_IP` 不一致 | 全部统一为 `127.0.0.1` |
| Topic 双方存在但回调可能无数据 | 传感器 QoS 可能不兼容 | 检查 Reliability，必要时用 `SensorDataQoS` |
| 到点后提示没有相机图像 | `if (latest_image_)` 判断写反 | 改为 `if (!latest_image_)`；warning 实际说明很可能已有图像 |
| 图片保存失败 | 转换、目录、权限或写入问题 | 分开检查 `cv_bridge` 异常和 `imwrite` 返回值 |
| 类名已改但日志仍显示旧节点名 | 构造函数仍是 `Node("navigate_to_pose_client")` | 改为语义一致的 `Node("patrol_controller")`，便于查询和读日志 |

## 八、形成的排错方法

1. **先查接口再写字段。** 用 `ros2 interface show` 查看本机 Action/Service 生成定义，不用记忆混写类型。
2. **按通信边界逐段验证。** Nav2 从 action list 到 result；Speech 从独立 service call 到巡检回调；Camera 从 Gazebo topic 到 bridge、ROS publisher、subscriber；Photo 从非空消息到转换、写盘和文件存在。
3. **从第一条真实编译错误开始。** 接口或依赖错误会引起大量级联红线，不能把每一条都当独立问题。
4. **结合代码分支解释日志。** `No camera image received yet` 正是反例：回到触发它的 `if` 后，才发现日志与真实状态相反。

## 九、最终数据流

```text
Gazebo Camera
    ↓ gz.msgs.Image
ros_gz_bridge（与 Gazebo 共用 GZ_IP）
    ↓ sensor_msgs/msg/Image on /camera/image
PatrolController image_callback → latest_image_
    ↑
FollowWaypoints Feedback/Result → 到达巡检点
    ├── SpeechText Client → /speech_text → speaker/espeak-ng
    └── cv_bridge → OpenCV → photo_<点名>.jpg
```
