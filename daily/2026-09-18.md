## 今日真正掌握

### 1. `server_sock` 与 `client_sock`

- `server_sock` 经 `socket → bind → listen` 成为监听 Socket，只负责等待新连接。
- `accept(server_sock, ...)` 返回新的 `client_sock`，服务端通过它与某一个客户端收发数据。
- 一个监听 fd 可以先后 `accept()` 出多个连接 fd；`accept()` 不会把监听 fd 变成连接 fd。
- `fork()` 复制父进程的 fd 表，父子进程中的同名 fd 引用相同的内核 Socket 对象。

多进程 Server 的职责划分：

```text
父进程：保留 server_sock
        close(client_sock)
        继续 accept 下一个客户端

子进程：close(server_sock)
        使用 client_sock 收发文件
        close(client_sock)
        _exit(0)
```

父进程若不关闭自己的 `client_sock` 引用，子进程关闭连接后，内核中仍有引用，连接资源不能按预期释放。子进程若不关闭监听 fd，会无意义地延长监听 Socket 的生命周期。子进程处理完成后必须退出，否则它会回到外层循环，对已关闭的 `server_sock` 再次调用 `accept()`。

### 2. 命令行参数与地址配置

客户端约定：

```text
./client <server_ip> <port> <filename>
```

对应 `argv[1]`、`argv[2]`、`argv[3]`。使用前应先检查 `argc == 4`，否则读取不存在的参数属于越界访问。`std::stoi(argv[2])` 将端口字符串转为整数；无有效数字时可能抛出 `invalid_argument`，超出范围时可能抛出 `out_of_range`。端口写入 `sockaddr_in::sin_port` 前使用 `htons()` 转成网络字节序；IPv4 文本地址使用 `inet_pton()`。

### 3. TCP 是字节流

TCP 只传输有序字节，不区分“文本模式”和“二进制模式”，也不保留一次 `send()` 的边界。`open + read + send` 已经是在发送原始字节，可用于文本、图片、PDF、ZIP 等文件。

正文长度必须使用 `read()` 的实际返回值 `n`：

```cpp
ssize_t n = read(file_fd, buffer, sizeof(buffer));
send_all(sock, buffer, n);
```

不能对二进制正文使用 `strlen(buffer)`，因为 `0x00` 会被当作字符串结束；也不能始终发送 `sizeof(buffer)`，因为最后一次读取通常不足一个完整缓冲区。把每个字节转为字符 `0`、`1` 会把数据量扩大约 8 倍，没有必要。

### 4. 文件信息和应用层协议

两端使用相同结构表示文件名和大小：

```cpp
struct file_Info
{
    char file_name[256];
    uint64_t file_size;
};
```

当天协议顺序：

```text
Client                                Server 子进程
file_Info ──────────────────────────→ recv_all(sizeof(file_Info))
          ←────────────────────────── send_all("OK", 2)
等待 OK
open → read → send_all ─────────────→ recv_file → recv → write
                                      累计 file_size 字节
```

ACK 表示服务端已经收到元信息、可以进入正文阶段。客户端收到完整的 `"OK"` 后才发送正文；服务端必须在发送 ACK 后**实际调用** `recv_file()`。只定义函数而不调用，不会创建接收文件。

### 5. `send_all()` / `recv_all()`

TCP 的一次 `send()` 或 `recv()` 可能只处理部分数据。完整读写要记录累计长度：

```text
本次地址 = ptr + total
本次长度 = len - total
成功后   total += n
```

`send()`、`recv()`、`read()`、`write()` 的返回类型是 `ssize_t`，因为失败时返回 `-1`。若用无符号 `size_t` 保存 `send()` 的返回值，`-1` 会变成很大的正数，错误判断可能失效。

### 6. 服务端保存文件

服务端根据元信息构造：

```cpp
string recv_name = "recv_" + string(file.file_name);
open(recv_name.c_str(), O_WRONLY | O_CREAT | O_TRUNC, 0644);
```

`std::string::c_str()` 提供 `open()` 需要的 C 字符串。`recv_file()` 每次最多读取：

```text
min(buffer 大小, file_size - total_received)
```

直到累计收到 `file_size` 字节，再关闭文件。`recv_` 前缀避免测试时直接覆盖源文件。

## 暴露的问题

1. 客户端 `main()` 在构造 `socket_client` 前没有检查 `argc`；直接运行 `./client` 会使 `argv[2]` 无效，并可能表现为 `stoi invalid_argument` 或其他未定义行为。
2. 两端 `send_all()` 把 `send()` 返回值保存为 `size_t`，应改为 `ssize_t`，否则 `-1` 不能可靠识别。
3. 客户端用一次 `read()` 等待 ACK。TCP 可能把两个字节拆开，应累计接收 2 字节并校验内容。
4. 服务端已经调用 `recv_file()`，但没有检查返回值；子进程完成后也没有 `close(client_sock) + _exit(0)`，可能回到外层循环并对已经关闭的监听 fd 调用 `accept()`。
5. 服务端文件 `write()` 只调用一次，没有处理磁盘短写；严格实现还需要 `write_all()`。
6. `fork()` 失败路径、`EINTR`、`SIGPIPE/EPIPE`、子进程回收尚未完整处理。
7. 直接发送 C++ 结构体内存依赖两端相同的结构布局、字节序和整数表示。`file_size` 尚未序列化为明确的网络格式，不是跨平台通用协议。
8. 当前 `"OK"` 只表示元信息已收到，不表示整个文件已落盘成功；协议还没有“传输完成”ACK、校验和与失败清理。
9. `bind: Address already in use` 需要先用 `perror("bind")` 获得真实错误，再检查旧服务是否仍占用 8080。`SO_REUSEADDR` 可帮助处理部分重启场景，但不能让两个正在监听的服务同时占用同一地址。
10. `recv_` 只降低误覆盖源文件的风险；同名接收文件仍会被 `O_TRUNC` 覆盖，也没有限制路径、大小、超时或中途断开后残留文件，当前仅适合可信实验环境。
