# 二、IPC 是什么

IPC 全称：

```text
Inter-Process Communication
进程间通信
```

Linux 中，不同进程默认拥有彼此独立的虚拟地址空间，因此一个进程不能直接访问另一个进程的普通变量。

IPC 用于解决：

```text
进程默认彼此隔离
        ↓
多个进程又需要协作
        ↓
需要通信、共享、通知、同步
        ↓
IPC
```

常见 IPC：

```text
pipe
FIFO
mmap
Shared Memory
Message Queue
Signal
Semaphore
Socket
```

---

# 三、FIFO 命名管道

FIFO：

```text
First In First Out
Named Pipe
命名管道
```

它允许两个没有父子关系的独立进程通信：

```text
mysender
   │
 write()
   ↓
 myfifo
   │
 read()
   ↓
myreader
```

创建 FIFO：

```bash
mkfifo myfifo
```

C/C++：

```cpp
mkfifo("myfifo", 0666);
```

如果已存在：

```cpp
if (mkfifo("myfifo", 0666) == -1)
{
    if (errno != EEXIST)
    {
        perror("mkfifo");
        return 1;
    }
}
```

# 四、FIFO 的阻塞机制

写端：

```cpp
open("myfifo", O_WRONLY);
```

如果没有 reader：

```text
open(O_WRONLY)
↓
没有读端
↓
阻塞
```

读端：

```cpp
open("myfifo", O_RDONLY);
```

如果没有 writer：

```text
open(O_RDONLY)
↓
没有写端
↓
阻塞
```

因此：

```bash
echo "hello" > myfifo
```

如果没有读端，也会被阻塞。

# 五、FIFO sender / reader

## sender

```cpp
int fd = open("myfifo", O_WRONLY);

if (fd == -1)
{
    perror("open");
    return 1;
}

std::string message = "Hello, World!";
write(fd, message.c_str(), message.size());

close(fd);
```

## reader

```cpp
int fd = open("myfifo", O_RDONLY);

if (fd == -1)
{
    perror("open");
    return 1;
}

char buffer[256];

ssize_t n = read(fd, buffer, sizeof(buffer) - 1);

if (n == -1)
{
    perror("read");
    close(fd);
    return 1;
}

if (n > 0)
{
    buffer[n] = '\0';
    std::cout << buffer << std::endl;
}

close(fd);
```

# 六、`read()` 返回值

```cpp
ssize_t n = read(fd, buffer, size);
```

含义：

```text
n > 0
→ 成功读取 n 个字节

n == 0
→ EOF
→ 所有写端关闭且数据已读完

n == -1
→ 读取失败
```

今天出现过错误判断：

```cpp
if (n != -1)
{
    perror("receive");
}
```

这会导致读成功时反而进入错误分支，出现：

```text
receive: Success
```

正确写法：

```cpp
if (n == -1)
{
    perror("read");
}
```

# 七、为什么要 `buffer[n] = '\0'`

`read()` 读取的是原始字节，不会自动补 C 字符串结束符。

所以：

```cpp
buffer[n] = '\0';
```

用于把：

```text
h e l l o
```

变成：

```text
h e l l o \0
```

因此通常：

```cpp
read(fd, buffer, sizeof(buffer) - 1);
```

要预留一个字节给 `\0`。

---

# 八、FIFO 连续读取与 EOF

```cpp
while (true)
{
    ssize_t n = read(fd, buffer, sizeof(buffer) - 1);

    if (n == -1)
    {
        perror("read");
        break;
    }

    if (n == 0)
    {
        std::cout << "Sender disconnected." << std::endl;
        break;
    }

    buffer[n] = '\0';
    std::cout << buffer << std::endl;
}
```

`read() == 0` 不是错误，而是 EOF。

# 九、FIFO 是字节流

非常重要：

```text
write() 次数 ≠ read() 次数
```

例如：

```cpp
write(fd, "ABC", 3);
write(fd, "DEF", 3);
```

reader 可能一次：

```cpp
read(...)
```

就得到：

```text
ABCDEF
```

所以 FIFO 没有天然的“消息边界”，需要应用层自己设计分隔方式，例如：

```text
Hello\n
Linux\n
IPC\n
```

规定 `\n` 表示一条消息结束。

# 十二、`mmap()` 内存映射

`mmap`：

```text
memory mapping
内存映射
```

传统文件访问：

```text
文件
 ↓
read()
 ↓
buffer
 ↓
程序
```

`mmap()`：

```text
文件
 ↕
映射关系
 ↕
进程虚拟地址空间
 ↓
指针
```

程序可以通过：

```cpp
data[0]
data[1]
data[2]
```

直接访问映射区域。

它不是简单“把整个文件复制进 RAM”，而是建立文件与虚拟地址之间的映射关系。

---

# 十三、与 STM32 FMC 的类比

FMC：

```text
CPU 地址
   ↓
FMC 地址映射
   ↓
外部设备
```

Linux mmap：

```text
进程虚拟地址
     ↓
Linux 虚拟内存系统
     ↓
文件 / 共享对象
```

共同点：

```text
程序访问的是一个地址，
但这个地址背后对应的是另一个资源。
```

区别：

```text
FMC  → 硬件地址/总线映射
mmap → 操作系统虚拟内存映射
```

---

# 十四、`mmap()` 六个参数

函数：

```cpp
void *mmap(
    void *addr,
    size_t length,
    int prot,
    int flags,
    int fd,
    off_t offset
);
```

## 1. `addr`

常用：

```cpp
nullptr
```

表示让 Linux 内核选择映射起始地址。

## 2. `length`

例如：

```cpp
2048
```

表示映射区域长度为 2048 字节。

## 3. `prot`

常见：

```cpp
PROT_READ
PROT_WRITE
PROT_EXEC
PROT_NONE
```

例如：

```cpp
PROT_READ | PROT_WRITE
```

表示可读可写。

## 4. `flags`

最重要：

```cpp
MAP_SHARED
MAP_PRIVATE
```

`MAP_SHARED`：修改可被其他共享映射进程观察到，适合 IPC。

`MAP_PRIVATE`：私有映射，涉及 Copy-on-Write（写时复制）。

## 5. `fd`

表示映射哪个文件。

## 6. `offset`

例如：

```cpp
0
```

表示从文件开头开始映射。

完整示例：

```cpp
void *ptr = mmap(
    nullptr,
    4096,
    PROT_READ | PROT_WRITE,
    MAP_SHARED,
    fd,
    0
);
```

# 十八、为什么出现 `Bus error`

今天出现：

```text
Bus error (core dumped)
```

关键原因：

```text
mmap 的 length 变大
≠
底层文件自动变大
```

例如：

```text
shared.dat = 0 bytes
mmap       = 256 bytes
```

然后：

```cpp
std::memset(data, 0, 256);
```

会访问没有合法底层文件空间支撑的区域，可能触发 `SIGBUS`。

---

# 十九、`ftruncate()`

用于调整文件实际大小：

```cpp
ftruncate(fd, 256);
```

正确顺序：

```text
open()
 ↓
ftruncate(fd, 256)
 ↓
文件真正成为 256 bytes
 ↓
mmap(..., 256, ...)
 ↓
访问映射区域
```

必须区分：

```text
文件大小
→ ftruncate / st.st_size

映射长度
→ mmap 的 length
```

# 二十二、为什么两个 `.cpp` 不能一起编译

今天执行：

```bash
g++ read.cpp write.cpp -o main
```

出现：

```text
multiple definition of `main'
```

因为：

```text
read.cpp  → 有 main()
write.cpp → 也有 main()
```

它们是两个独立程序，应分别：

```bash
g++ read.cpp -o read_main
g++ write.cpp -o write_main
```

多个 `.cpp` 可以一起编译，但最终只能有一个 `main()`。

# 二十四、mmap 的同步问题

`mmap` 解决的是：

```text
两个进程如何共享同一份数据
```

但没有自动解决：

```text
谁先读？
谁先写？
什么时候可以读？
什么时候可以写？
```

所以：

```text
共享 ≠ 同步
```

可以先用教学版标志位理解：

```text
byte 0      → ready
byte 1~255  → message
```

writer：

```cpp
data[0] = 0;

std::memcpy(
    data + 1,
    message,
    std::strlen(message) + 1
);

data[0] = 1;
```

reader：

```cpp
while (data[0] == 0)
{
}

std::cout << data + 1 << std::endl;
```

这种：

```cpp
while (data[0] == 0)
{
}
```

称为：

```text
Busy Waiting
忙等待
```

会持续占用 CPU，因此后面需要学习更正式的同步机制。

# 二十六、今日重点错误总结

1. FIFO 文件名 `myfifo` 曾误写成 `myfilo`。
2. `read()` 错误判断应是 `n == -1`，不是 `n != -1`。
3. `read() == 0` 表示 EOF，应及时 `break`。
4. 修改 `.cpp` 后必须重新编译。
5. 两个都含 `main()` 的 `.cpp` 不能链接成一个程序。
6. `mmap()` 映射长度大于底层文件有效长度后进行访问，可能触发 `Bus error`。
7. `ftruncate()` 用于真正调整文件大小。
8. FIFO 的 `write()` 次数不等于 `read()` 次数。
9. FIFO 是字节流，没有天然消息边界。
10. mmap 解决共享问题，但不自动解决同步问题。

# 二十八、FIFO 与 mmap 对比

| 特性 | FIFO | mmap + MAP_SHARED |
|---|---|---|
| 核心思想 | 传输数据 | 共享数据 |
| 主要操作 | `read/write` | 指针访问 |
| 数据模型 | 字节流 | 共享区域 |
| 消息边界 | 无 | 由数据结构决定 |
| 是否要求父子关系 | 不要求 | 不要求 |
| 同步问题 | 视场景而定 | 通常很重要 |

简单理解：

```text
FIFO：
“我把数据发送给你。”

mmap：
“我们都访问这块公共区域。”
```
